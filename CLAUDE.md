# copilot-key — project notes for Claude Code

Context for anyone (human or agent) picking this repository up. Written in
English like everything else in the repo; conversation with the maintainer is
in German.

## What this is

A launcher bound to the Copilot key of the Minisforum AI X1 Pro, running on
Linux Mint 22.3 (Cinnamon, X11, Ubuntu 24.04 base). One press toggles a
window, a double press opens a radial overlay menu, every state change plays
its own audio cue. The menu is filled either in a GTK editor or in the wheel
itself, both listing the installed applications, so using the thing never
requires opening a config file. Skins decide what the wheel looks like.

Published at https://github.com/SoulInfernoDE/copilot-key-linux (public,
`main`, released as `v1.0.0`).

## Layout

```
bin/copilot-key          launcher: press logic, radial + list menu, cue triggering
bin/copilot-sound        cue playback, tries players until one really succeeds
bin/copilot-config       GTK editor for the menu: entries, app search, skins
lib/i18n.sh              string catalogue for the shell scripts
config/config.toml       config template (English), config.de.toml (German)
config/keyd-copilot.conf keyd rule for the Copilot chord
config/copilot-key-config.desktop     start menu entry for the editor
config/copilot-key-autostart.desktop  per-user setup at login
skins/                   three shipped skins, format in docs/skins.md
sounds/                  the glass bells (eight CC0 cues) plus crystal/ and felt/,
                         all generated by tools/generate_sounds.py;
                         format in docs/sound-themes.md
install.sh uninstall.sh  installer / uninstaller
detect-key.sh            reports what the key actually emits
doctor.sh                checks install, audio chain, keyd, shortcut, libraries
```

## How the key reaches the launcher

The key sends no code of its own — it sends `LeftMeta+LeftShift+F23`, which
desktops will not accept as a shortcut. Hence the two-stage chain:

```
Copilot key → keyd (evdev) → Ctrl+Alt+Shift+F12 → desktop shortcut → copilot-key
```

keyd sits below the window system, so the same setup works on X11 and Wayland.
Other firmware revisions emit other codes; `detect-key.sh` reports the truth
and `config/keyd-copilot.conf` carries the alternatives commented out.

## Press semantics

1. Menu already open → the press closes it (PID file in `$XDG_RUNTIME_DIR`).
2. Double press within `double_press_ms` → always open the menu.
3. Otherwise `single_press`: `toggle_or_menu` (default), `toggle` or `menu`.

Toggling uses `wmctrl`/`xdotool`: the window is activated, or minimised when it
is already the active one.

## Where things are installed

`./install.sh` is system-wide by default (`--user` restores the old
`~/.local` layout): programs in `/usr/local/bin`, sounds and skins in
`/usr/local/share/copilot-key`, the editor's launcher in
`/usr/local/share/applications`, a login hook in `/etc/xdg/autostart`.

What stays per user: the configuration, the skins they write themselves and
the keyboard shortcut. `copilot-key ensure-shortcut` does both halves of that
setup - it writes `~/.config/copilot-key/config.toml` from the defaults if it
is missing and registers the Cinnamon binding - and the autostart entry runs
it once per login, which is how a second user on the machine ends up with a
working key and a menu of their own. `install.sh` calls the same command
instead of carrying its own copy of the gsettings dance.

`data_dirs()` is the single answer to "where is the installed data": the
user's share directory, everything in `XDG_DATA_DIRS`, `/usr/local/share`,
`/usr/share`, and `<prefix>/share/copilot-key` for other prefixes. Started
from a git checkout (recognised by `install.sh` next to `bin/`), the checkout
comes first - otherwise an installed copy would quietly shadow every change to
`skins/` or `sounds/` until the next install. Sounds and skins are both looked
up through it.

## Editing the menu

Two front ends, one implementation underneath. The launcher owns everything
both of them need, and `bin/copilot-config` imports it through `importlib`
(the launcher has no `.py` suffix, so the loader is named explicitly) -
`STRINGS`, `tr()`, `draw_icon()`, `icon_for()`, `dump_config()`,
`save_config()`, `normalise_config()`, `read_apps()`, `load_skin()` and the
button painters. Importing it is safe because everything at module level there
is a constant or a pure function.

- **The writer.** `dump_config()` renders the whole `config.toml` including its
  comments. The shipped templates are printed from it -
  `bin/copilot-config --print-template`, language from the environment - so the
  comments exist exactly once. Regenerate both after touching them.
- **The app search.** `read_apps()` walks the XDG `applications` directories
  (plus the Flatpak exports, which are missing from `XDG_DATA_DIRS` in some
  sessions), honours `NoDisplay` / `Hidden` / `TryExec`, strips the `%f`-style
  field codes out of `Exec` and takes `StartupWMClass` as the window class.
  Picking an app fills label, subtitle, command, window class and icon at once.
- **The wheel's own editor.** `RadialMenu` keeps the whole overlay: the centre
  button reveals two tools, the pencil switches into edit mode, where items are
  dragged to reorder (`order()` re-flows them live around `drop_slot()`), a
  placeholder appends one, and clicking a button opens the Cairo-drawn search
  panel - the wheel shrinks and moves below it while the button being filled
  pulses. Every committed change goes straight to disk; placeholders that never
  got an application are dropped instead of being saved.
- **Two searches, one panel.** `search_mode` is `app` or `icon`. The icon mode
  is opened by the picture badge on a button and lists the drawn symbols
  followed by every application that carries an icon; clicking the pulsing
  button itself is the "use the original icon" answer. `take_hit()` writes
  `app_icon` plus `icon_source`, which is the per-button override of the
  `use_app_icons` setting - `themed_icon_for()` is the one place that decides,
  for both menus and both previews.
- **Nothing jumps.** Buttons are not placed at their slot angle; `tween()`
  eases each one towards it every frame (shortest way round the circle) and
  everything that appears grows in from a quarter of its size. Reordering,
  adding, removing and entering edit mode all animate through that one
  mechanism, and hit testing follows what was drawn: `draw_items()` records
  `self.boxes`, `hit()` tests against them.

`@configure` in an action's `command` starts the editor window; `copilot-key
configure` does the same from a terminal. `@edit-config` still opens the raw
file for anyone who prefers it.

## Application icons

`use_app_icons` in `[general]` puts the real icons on the buttons.
`resolve_app_icon()` finds the desktop entry a command belongs to and borrows
its icon, which is what makes the setting work for entries written by hand.
The `@placeholders` are followed to the program they really start -
`@claude-desktop` to Claude's own desktop file, `@terminal` to the emulator
`chosen_terminal()` picks (through the `x-terminal-emulator` alternatives
link), `@browser` and `@edit-config` to the user's default handlers, and
`@configure` to the editor's own entry - with a freedesktop stand-in such as
`utilities-terminal` as the last resort. `flatpak run ...` commands match by
their full Exec line only, since the launcher's own name says nothing;
the result is cached per command, and the lookup runs from a timeout after the
first frame so the wheel is never late. Entries created by either editor
remember the icon as `app_icon` right away, so nothing has to be resolved for
them.

## Skins

A skin is a TOML file with colours, a `shape` (circle or rounded) and a
`style` (`flat`, `glass`, `mint`). `Skin` merges it over the built-in one, so
partial skins work the same way partial translations do. `paint_button()` and
`button_icon_rgba()` are the only places that know what a style looks like -
both menus and both previews go through them, which is why the editor's
preview matches the real wheel. `available_skins()` searches the user's config
directory first, then the data dirs; the format is documented in
`docs/skins.md`, which the editor links to.

## Sound themes

A theme is a directory of cue files plus an optional `theme.toml`. The glass
bells are the flat `sounds/` directory itself; every other theme is a
sub-directory, in a data dir or in `~/.config/copilot-key/sounds/`.
`CueResolver` decides what plays, as a cascade: `[sounds]` in the config (one
file per cue, or `"none"`), then the active theme, then whatever it
`inherits`, then the glass bells. Themes may therefore be partial, like skins
and translations. `sound_theme = "auto"` takes the skin's `sound_theme`.

The launcher resolves the file and hands `copilot-sound` a path; the old
"cue name plus `COPILOT_KEY_SOUND_DIR`" call still works, which is what
`doctor.sh` uses. Files picked in the editor are copied into the user's sound
directory - compared by content, so picking the same file twice reuses it.

Every save path carries `[sounds]` through `normalise_config()`: the wheel's
edit mode saves the actions it changed and must not take the hand-picked cues
with them. Tested by reordering in the wheel and reading the file back.

## Conventions

- Code comments, README, commit messages, release notes: English.
  `README.de.md` is the German counterpart, both link to each other.
- No hard-coded user-visible text. Everything goes through a catalogue with
  English as the base: `STRINGS` + `tr()` in `bin/copilot-key`, `T_EN`/`T_DE` +
  `t()` in `lib/i18n.sh`. Language comes from `COPILOT_KEY_LANG`, else
  `LC_ALL` / `LC_MESSAGES` / `LANG`; a missing key falls back to English on its
  own, so partial translations are fine.
- Adding a language: one dict in `STRINGS`, one `T_<CODE>` array plus a branch
  in `copilot_lang`, optionally `config/config.<code>.toml`.
- No third-party assets: icons are Cairo paths, sounds are synthesised.

## Gotchas worth knowing

- **Menu closing instantly.** The overlay dismisses on focus loss, but only
  after it actually had focus and 0.6 s have passed. Without those guards it
  vanishes wherever the WM bounces focus while mapping. `close_on_focus_loss`
  turns the behaviour off entirely.
- **Transparency.** The overlay paints its own background with Cairo
  (`OPERATOR_SOURCE`). Setting a background via CSS on an app-paintable RGBA
  window does *not* work — that bug let the desktop shine through.
- **`cr.new_path()` before every arc.** Cairo otherwise joins the arc to
  wherever the previous path or a Pango layout left the pen, which draws stray
  diagonal lines across the screen.
- **python3-gi-cairo is required** for the radial menu. `cairo_available()`
  checks the bridge once and falls back to the list menu with a warning.
- **Audio.** Players are tried until one exits 0 — `pw-play` rejects Ogg Vorbis
  in some builds, so "player installed" is not "player works".
  `COPILOT_KEY_DEBUG=1` reports which one took the file.
- **`install.sh` never overwrites an existing `~/.config/copilot-key/config.toml`.**
  Re-running it after an update is safe.
- **`invalidate_sort()` only queues the re-sort.** Asking a `GtkListBox` for
  its first row right afterwards still answers in the old order, which left the
  app search with a filtered-away row selected - Enter then picked an
  application the user could not even see. The editor determines the best match
  itself instead of asking the list.
- **The config templates are generated.** They are the editor's own output, not
  hand-written files; edit the comments in `bin/copilot-config` and print them
  again.
- **Test saves need a throwaway `XDG_CONFIG_HOME`.** The editor and the
  wheel's edit mode both write to the real
  `~/.config/copilot-key/config.toml` otherwise - which is also how "Test the
  menu" stays harmless: it drops the unsaved state into a temporary config
  home and starts the genuine menu against that. dconf follows the same
  variable, so `gsettings` inside such a test answers with schema defaults
  rather than the desktop's real settings - handy for trying
  `ensure-shortcut` without touching the session, confusing when a theme
  lookup suddenly disagrees with the desktop.
- **`gtk-application-prefer-dark-theme` is not enough.** Mint and Yaru ship
  their dark versions as separate themes, and Mint puts the word in the
  middle of a colour variant: `Mint-Y-Aqua` -> `Mint-Y-Dark-Aqua`, not
  `Mint-Y-Aqua-Dark`. `dark_variant()` / `light_variant()` look the twin up in
  the theme directories and fall back to the property alone (which is all
  Adwaita needs).
- **A `palette` written below `[colors]` belongs to that table.** Plain TOML,
  but every skin author trips over it once, so the loader accepts it in both
  places and `docs/skins.md` warns about it.
- **The frosted search panel needs the screen before the overlay is mapped.**
  `grab_backdrop()` runs in `run()` while the window is still invisible;
  afterwards the root window would only hand back our own dimmed copy. The
  blur is two bilinear `scale_simple()` passes (far down, then back up), which
  GdkPixbuf does in C - a box blur written in Python would not survive 60 Hz.
  The grab costs under 3 ms, the result is cached per panel size, and without
  it the panel simply falls back to an opaque fill.
- **`draw_icon()` starts with `cr.new_path()`.** The arcs inside it would
  otherwise be joined to wherever the previous drawing left the pen - a Pango
  layout in the search results was enough to draw a diagonal line across the
  panel.

## Verifying changes

```bash
bash -n install.sh uninstall.sh detect-key.sh doctor.sh lib/i18n.sh
python3 -m py_compile bin/copilot-key bin/copilot-config tools/generate_sounds.py
python3 tools/generate_sounds.py sounds      # regenerates the cues (see below)
COPILOT_KEY_LANG=en bin/copilot-config --print-template | diff - config/config.toml
COPILOT_KEY_LANG=de bin/copilot-config --print-template | diff - config/config.de.toml
./doctor.sh                                  # full environment check
```

Every skin should be rendered once after touching the painters - `menu_skin`
in the throwaway config, then `copilot-key menu` per skin.

The menu can be rendered headlessly for visual review:

```bash
Xvfb :99 -screen 0 1280x800x24 &
DISPLAY=:99 LANG=en_US.UTF-8 ./bin/copilot-key menu &
DISPLAY=:99 import -window root /tmp/menu.png
```

The editor the same way, with a disposable config home so a test save cannot
touch the real one. Capture its window rather than the root: without a window
manager the root keeps the leftovers of everything drawn before.

```bash
DISPLAY=:99 XDG_CONFIG_HOME=/tmp/cfg LANG=en_US.UTF-8 ./bin/copilot-config &
DISPLAY=:99 import -window "$(DISPLAY=:99 xdotool search --class copilot-config | tail -1)" \
    /tmp/editor.png
```

`xdotool` also drives it: `mousemove <x> <y> click 1`, `type`, `key Return`.

Check both `LANG=en_US.UTF-8` and `LANG=de_DE.UTF-8` after touching any text.

## Sound design

Eight cues, one family: soft glass bells on a pentatonic scale over D, under
0.9 s, peak −18 dBFS, gentle attack. Three rules learned the hard way, all
from cues that sounded slightly out of tune:

- Move between notes in steps, not glides. A decaying bell that drifts sounds
  detuned in either direction: `toggle-hide` sagged by two thirds of a
  semitone, `toggle-show` rose by half of one. The drag cues keep their bends
  on purpose - a pluck and a plop are gestures, not notes.
- Where notes overlap, tune the interval pure (`FS5_PURE` = D5 × 5/4). Equal
  temperament puts the major third 14 cents sharp, which a melody hides and
  two ringing bells do not.
- The default bell has an inharmonic partial at 3.01 × the fundamental. Alone
  it is the glassy shimmer; next to another note it can land a few Hz from one
  of that note's partials and beat - in `menu-open` D5's third partial and
  A5's second were 7.9 Hz apart, so that cue now uses pure fifths
  (`A4_PURE`, `A5_PURE`) and leaves the partial out. Measure before blaming
  the ears.

Only the glass bells are tuned by hand. The other themes are derived: every
cue keeps one gesture in `GESTURES` - pure ratios over a root, rising for
open and show, falling for dismiss and hide - and a theme in `THEMES` picks
only the root, the timbre (purely harmonic partials) and the decay. Nothing
can drift or beat, and a new theme is ten lines. `generate_sounds.py sounds
<theme>` builds just that one and leaves the rest of `sounds/` alone.

`tools/generate_sounds.py` builds them
with additive synthesis in numpy and encodes to Ogg via ffmpeg — no samples, no
recordings, which is what keeps them CC0.

The synthesis is deterministic, but the Ogg header carries the encoder version
(`Lavf58.76.100` in the committed files). A different ffmpeg therefore produces
byte-different files with identical audio — `git checkout -- sounds/` after a
regeneration run unless the cues themselves changed.
